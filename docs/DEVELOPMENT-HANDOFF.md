# PRIZM 개발 인수인계

작성 기준: 2026-09-23 현재 로컬 데모

## 1. 제품 목표

PRIZM은 제조 AI의 데이터 준비, 코드 실행, 모델 평가, 승격, 배포, 모니터링, 개선 작업을 하나의 운영 흐름으로 연결하는 포털이다. 현재 저장소는 이해관계자 시연과 요구사항 구체화를 위한 고해상도 목업이며, 일부 실행·편집 기능은 실제 백엔드와 연결된다.

주 사용자는 ML 엔지니어, 공장 엔지니어, PM, 담당 임원, 플랫폼 관리자다. 제조솔루션본부 약 1,000명이 사용하는 엔터프라이즈 포털을 전제로 한다.

## 2. 핵심 데모 시나리오

1. 모델 모니터링에서 미세 크랙 미검출 증가를 감지한다.
2. ML 엔지니어와 공정 엔지니어에게 병렬 확인 작업이 생성된다.
3. `나의 작업`에서 이상 원인과 현장 판단을 기록한다.
4. 외부 이미지 카탈로그에서 저신뢰 이미지를 선별·라벨링하고 기존 데이터셋에 결합한다.
5. 데이터 자산에 새 버전이 등록된다.
6. 실험 대시보드에서 코드 자산과 데이터 ID를 선택해 학습 파이프라인을 실행한다.
7. Airflow가 Papermill 기반 노트북을 실행하고 MLflow에 결과를 남긴다.
8. 평가 관리에서 일반 사용자도 결과 이미지와 성능을 검토하고 모델을 승격한다.
9. Production 모델을 즉시 배포하거나 배포 관리에서 나중에 배포한다.
10. 모니터링에서 재학습·승격·배포 이후 상태와 전체 회사→공장→과제/모델로 이어지는 현황을 확인한다.

이 흐름을 변경할 때는 화면 하나의 편의보다 폐루프 전체의 연결성을 우선한다.

## 3. 정보 구조

- 나의 작업: 할 일, 작업 이력
- 대시보드: 홈, 오늘의 작업, 거점 운영, 파이프라인 현황, 성과 근거, 재무 기여
- 과제관리
- 데이터관리: 이미지 카탈로그, 데이터 연결 매뉴얼
- 자산관리: 모델, 코드, 데이터, 파이프라인 구성, 개발 매뉴얼, SDK 매뉴얼
- 실행관리: 실험 대시보드
- 평가관리: 모델 평가, 자동 평가 기준 관리
- 배포관리
- 모니터링
- 자원관리: 실행 자원, 실행 환경
- 관리자

좌측 메뉴는 여러 업무 화면에서 `code-assets-workspace.tsx`의 내비게이션을 공유한다. 메뉴를 바꾸면 홈의 `app/page.tsx`와 다른 워크스페이스에서 동일하게 보이는지 확인한다.

## 4. 화면 구조와 공통 컴포넌트

`PortalGradientBackground`가 페이지 전반의 샌드·청회색·옅은 보라 배경을 제공한다. `PortalPageFrame`, `PortalPageHeader`, `PortalButton`, `PortalFilterSurface`, `PortalResultsSurface`가 업무 화면의 패딩, 제목, 버튼, 필터, 결과 영역을 맞춘다.

자산 목록은 카드 기반 탐색이며 상세는 다음 순서를 공유한다.

`거점/과제 → 자산 제목·ID → 버전·등록자·메타정보 → 행동 → 탭 → 본문 + 우측 정보 패널`

코드 자산 상세는 Kaggle의 문서 중심 읽기 경험을 참고했지만 PRIZM의 탭, 헤더, 우측 패널, 색 체계를 유지한다. 스크롤하면 제목·핵심 행동이 축약되어 남고, 우측 패널은 노트북·실행 환경·버전 이력의 문맥 정보를 제공한다.

## 5. 자산 식별과 버전 규칙

- 과제: `PRJ000212`
- 데이터: `PRJ000212-D-0001`
- 코드: `PRJ000212-C-0001`
- 모델: `PRJ000212-M-0001`
- 버전: 날짜와 당일 순번을 알 수 있는 `260402-0001` 형식을 지향한다.

현재 일부 목업에는 `v2.4.1`, `v2.5.0` 형식이 남아 있다. 실제 메타데이터 모델을 확정할 때 일괄 마이그레이션하며 화면별로 임의 변경하지 않는다.

## 6. 프론트엔드와 백엔드 경계

### 프론트엔드에 있는 것

- 메뉴·업무 탭·대부분의 자산 카드와 상세 데이터
- 브랜드 브로셔와 홈 애니메이션
- 작업, 평가, 모니터링의 시연 흐름
- 정적 노트북 HTML 뷰어
- 실행 요청 및 SSE 표시 UI
- JupyterLab 편집 세션을 여는 포털 릴레이

### `prizm-backend`에 있는 것

- 실행 요청 검증과 실행 이력 저장
- Airflow DAG 트리거와 상태 추적
- 실행 노트북·로그·MLflow 결과 제공
- requirements 기반 실행 환경 이미지 준비
- JupyterLab 편집 컨테이너 생성·재사용·종료
- 편집 결과의 새 코드 자산 버전 등록

### 외부 MLOps 스택에 있는 것

- Airflow, MLflow, AI Hub/자산 API, MinIO 또는 호환 오브젝트 스토리지
- Papermill 실행 DAG와 데모 노트북
- 실행/편집용 Docker 베이스 이미지

외부 스택은 현재 두 GitHub 저장소에 포함되지 않는다. 사내 환경에서는 Sonnet/Claude Code가 이 경계를 임의로 대체하지 말고, 사내 Airflow·MLflow·오브젝트 스토리지 엔드포인트와 인증 방식을 먼저 확인해야 한다.

## 7. 실행 연계

`lib/prizm-api.ts`의 기본 API 주소는 `http://localhost:8081`이다. 코드 자산 상세 또는 실험 대시보드가 `POST /api/runs`를 호출하면 백엔드가 Airflow를 트리거한다. 진행 상태는 SSE로 전달되며 완료 후 노트북 셀 출력과 MLflow 결과를 표시한다.

목업 실행 이력은 `source: 'mock'`, 실연동 결과는 `source: 'live'`로 구분한다. mock만 자동 진행시키는 현재 규칙을 보존한다.

## 8. PRIZM Lab 편집 연계

1. 브라우저가 포털의 `POST /api/edit-sessions`를 호출한다.
2. 포털이 `prizm_user_id` HttpOnly 쿠키를 발급하고 백엔드에 소유자 ID와 자산/버전을 전달한다.
3. 백엔드가 Docker로 JupyterLab 컨테이너를 시작하고 노트북을 준비한다.
4. 브라우저는 `/edit/{sessionId}/...` 경로로 JupyterLab을 연다.
5. 포털은 요청마다 백엔드에서 세션 소유권과 상태를 확인하고 Jupyter 토큰을 서버 측에서만 주입한다.
6. 새 버전 등록은 `/edit-session-register/{sessionId}`를 통해 백엔드로 전달한다.

로컬 vinext/miniflare에서 Jupyter 커널 WebSocket 협상 문제가 있으므로 완전한 로컬 편집 검증에는 `scripts/edit-session-ws-relay.mjs`를 사용한다. 단순 화면 확인에는 필요 없다.

## 9. 디자인 원칙

- 현대자동차 Hyundai Blue, Sky Blue, Sand 계열을 기업 기반색으로 사용한다.
- PRIZM의 스펙트럼은 로고 Z와 빛의 분기 서사에 집중한다.
- 업무 화면은 따뜻한 밝은 배경, 흰 작업 면, 명확한 제목과 표로 구성한다.
- 카드 안에 카드를 반복하지 않는다.
- 색 선으로 모든 카드를 장식하지 않는다.
- 코드·데이터·모델 썸네일은 실제 제조 결과와 노트북 출력의 차이를 보여준다.
- 본문은 Pretendard, 코드·ID만 모노스페이스를 사용한다.
- 모달의 헤더와 하단은 불투명해야 하고, 버튼이 바닥에 붙지 않도록 여백을 유지한다.
- 공통 상세 화면에서 탭과 본문 간격, 우측 패널 폭, radius를 임의로 다르게 만들지 않는다.

세부 토큰은 `docs/design-system.md`, 판단 근거는 `design/PRIZM-DESIGN-HANDOFF.md`를 따른다.

## 10. 알려진 제약과 다음 작업

- 다수 메뉴는 준비 중 링크 또는 홈 앵커로 연결된다.
- 대부분의 데이터는 컴포넌트에 하드코딩된 시연 데이터다.
- 사용자 인증·과제별 RBAC·감사 로그는 UI만 있으며 실제 인증 시스템과 연결되지 않았다.
- 다운로드·SDK 스니펫·엑셀 내보내기 중 일부는 데모 상호작용이다.
- 실제 배포 관리, 모델 레지스트리 승격, 전사/공장/모델 모니터링 API는 후속 연동 대상이다.
- 자산 버전 표기 방식이 화면별로 혼재한다.
- 외부 MLOps 스택의 소스와 설치 자동화는 별도 관리 대상이다.
- `npm run lint`는 기반 UI와 기존 화면의 접근성·React Compiler 규칙 위반이 누적되어 실패한다. 빌드는 통과하며 lint 기준선 정리는 별도 작업이 필요하다.
- npm 의존성 감사에는 vinext/Vite/React Server Components 상위 버전 검증이 필요한 보안 항목이 남아 있다. 강제 업그레이드 전에 빌드·Workers 호환성과 전 화면 회귀를 확인한다.

## 11. 변경 완료 기준

- 요청한 화면만 변경되었다.
- 메뉴와 업무 탭의 순서가 이동하지 않는다.
- `npm run build`가 성공하고 `npm run lint` 결과에서 새 오류가 추가되지 않는다.
- 대상 화면을 데스크톱 해상도에서 직접 확인한다.
- sticky header, 탭, 모달, select, 우측 패널 접기 등 상태 변화도 확인한다.
- 실연동 실패가 목업 성공으로 표시되지 않는다.
- 새 환경 변수와 외부 의존성은 README와 이 문서에 함께 기록한다.
