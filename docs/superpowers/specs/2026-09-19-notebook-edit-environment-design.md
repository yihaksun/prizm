# 노트북 편집 환경 설계

- 작성일: 2026-09-19
- 상태: 설계 확정 대기
- 관련 문서: `2026-09-17-airflow-live-run-design.md` (실행 연동 설계)

## 1. 배경과 목표

코드 자산 상세 화면의 "코드 편집" 버튼은 현재 안내 문구만 띄운다. 이 버튼이 등록된
Notebook을 브라우저에서 바로 수정할 수 있는 환경(Colab과 같은 경험)을 열어주도록 만든다.

제약이 하나 더 있다. 개발환경 이미지는 12종 내외를 큐레이션해 버전관리로 제공하지만,
사용자는 코드 자산마다 임의의 패키지를 추가로 쓴다. 따라서 코드 등록 시
`requirements.txt`(또는 패키지 목록)를 입력받고, 그 패키지들이 설치된 환경을 제공해야 한다.

### 해결해야 할 핵심 문제: 체감 속도

순진하게 만들면 이런 흐름이 된다.

```
버튼 클릭 → 도커 기동(6.6초) → 패키지 설치(수십 초~수 분) → 화면 제공
```

실측(2026-09-19, macOS Docker Desktop, `prototype-airflow` 4.3GB 이미지):

| 구간 | 실측 |
|---|---|
| 컨테이너 시작 + 파이썬 기동 | 6.6초 |
| torch·ultralytics import 추가 | +1.8초 |

컨테이너 시작 6.6초 중 대부분은 macOS Docker Desktop의 VM 오버헤드이며, 리눅스 서버
배포 시 1~2초로 떨어진다. 즉 **컨테이너 기동은 본질적 병목이 아니다.** 진짜 병목은
패키지 설치다.

### 설계의 핵심 아이디어 두 가지

1. **설치 시점을 옮긴다.** 패키지 설치를 "편집 화면을 열 때"가 아니라 "코드를 등록할 때"
   수행한다. 등록 시점에 파생 이미지를 만들어 두면, 편집 열기는 이미 만들어진 이미지를
   기동하는 것뿐이다.
2. **에디터를 먼저 띄운다.** 노트북을 읽고 편집하는 데는 런타임이 필요 없다. 화면은 즉시
   전환하고 커널은 백그라운드로 연결하며 상태 칩만 표시한다. Colab이 빠르게 느껴지는
   가장 큰 이유가 이것이다.

## 2. 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 편집 환경과 실행 환경 | **동일한 파생 이미지 공유** | "편집할 땐 됐는데 실행하니 안 된다"는 문제를 구조적으로 제거. 실행 근거를 이미지 다이제스트로 고정해 감사 가능 |
| 패키지 소스 | **사내 미러(Nexus/Artifactory)** | 설정으로 분리해 프로토타입은 PyPI 직접, 운영은 미러로 전환 |
| 환경 빌드 시점 | **코드 등록/수정 시 자동 빌드** | 편집 열 때는 거의 항상 캐시 히트 → 체감 0초 |
| 편집 UI | **JupyterLab을 iframe으로 삽입** | 셀 편집·실행·출력 렌더링·커널 프로토콜을 직접 구현하지 않아 구현량이 압도적으로 적다 |

### 설계자 판단으로 결정한 사항

아래 세 가지는 승인 대기 중 판단으로 확정했다. 리뷰에서 뒤집을 수 있다.

**(가) 실행 경로 변경 위험을 감수한다.** 편집·실행 환경 통일을 선택한 이상 Airflow가
파생 이미지로 실행하도록 바꾸는 것은 필연이다. 위험은 §7에 완화책과 함께 기록한다.

**(나) 편집 중 상태와 자산 버전을 분리한다.** JupyterLab 자동저장은 드래프트이고, 자산의
새 버전이 되려면 사용자가 "새 버전으로 등록"을 눌러야 한다. 편집하다 만 코드가 자산
버전이 되면 재현성이 깨진다.

**(다) 두 단계로 나눈다.** Phase 1(환경 빌드 + 실행 통일)만으로도 "자산별 정확한 환경에서
실행된다"는 독립적 가치가 있고, Phase 2(편집 세션)의 전제가 된다.

## 3. 전체 구조

```
[코드 등록/수정]  requirements 입력
      |
      v  (백그라운드)
  캐시 키 계산 --> 레지스트리에 있으면 종료(0초)
      |                없으면
      v
  파생 이미지 빌드 --> 레지스트리 push --> 자산에 env_cache_key 기록
      |
      +----------------------------+
      v                            v
[편집] JupyterLab 컨테이너     [실행] Airflow가 같은 이미지로 papermill
   (Phase 2)                      (Phase 1)
```

## 4. 환경 빌드 파이프라인 (Phase 1)

### 4.1 캐시 키 — 설계의 척추

파생 이미지의 정체성은 세 값의 해시다.

```
cache_key = sha256(base_image_digest + "\n" + requirements_norm + "\n" + recipe_version)[:16]
```

- **`base_image_digest`**: 큐레이션 이미지의 **다이제스트**(`sha256:...`). 태그는 움직이므로
  키에 쓰지 않는다. 태그(`pytorch-2.4-yolo12-py311-cu124:v3`)는 표시·추적용으로 함께 저장한다.
- **`requirements_norm`**: 아래 규칙으로 정규화한 문자열.
- **`recipe_version`**: 빌드 레시피(Dockerfile 템플릿, 설치 도구) 버전을 나타내는 상수.
  이것을 키에 넣지 않으면 빌드 방식을 바꾼 뒤에도 낡은 이미지가 계속 캐시 히트한다.

같은 (베이스, requirements, 레시피) 조합은 **조직 전체에서 한 번만** 빌드된다. 다른 팀이
같은 조합을 등록하면 즉시 히트한다.

### 4.2 requirements 정규화 규칙

줄 순서만 다른 동일한 내용이 캐시 미스를 내면 안 되므로 정규화한다.

1. 주석(`#` 이후)과 빈 줄 제거, 각 줄 앞뒤 공백 제거
2. 패키지명을 PEP 503 규칙으로 정규화(소문자화, `_`·`.`·연속 `-`를 `-` 하나로)
3. extras 내부 정렬: `pkg[b,a]` → `pkg[a,b]`
4. 버전 지정자 내부 공백 제거: `torch >= 2.0` → `torch>=2.0`
5. 전체 줄을 사전순 정렬
6. 줄바꿈으로 결합

**거부 대상**: `-r other.txt`, `-e .`, `--index-url`, `--extra-index-url`, 직접 URL 참조.
중첩 참조는 해시 대상이 불명확해 재현성이 깨지고, 사용자가 index-url을 지정하면 사내 미러
정책을 우회한다. 등록 화면에서 즉시 거부하고 사유를 표시한다.

### 4.3 빌드 절차

1. requirements 파싱·정규화 → 캐시 키 계산
2. `environment_build` 테이블 조회. `READY` 레코드가 있으면 그것을 자산에 연결하고 종료
3. 없으면 `PENDING`으로 삽입하고 빌드 큐에 적재. 자산 상태를 `환경 빌드 중`으로 표시
4. 빌드 워커가 Dockerfile을 생성해 빌드한다
   ```dockerfile
   FROM <base_image_ref>@<base_image_digest>
   COPY requirements.txt /tmp/requirements.txt
   RUN uv pip install --system -r /tmp/requirements.txt
   ```
   - **uv 사용**: pip 대비 10~100배 빠르다. 일반적 requirements(5~20개) 기준 20~60초 예상
   - **사내 미러**: `PIP_INDEX_URL`·`UV_INDEX_URL` 환경변수로 주입. 설정값이라 환경별 교체 가능
   - BuildKit inline cache로 베이스 레이어 재사용
5. 성공 → `prizm/env:<cache_key>`로 push, 상태 `READY`, 자산 상태 `준비 완료`
6. 실패 → 상태 `FAILED`, 빌드 로그를 MinIO에 저장하고 요약 에러를 자산 화면에 노출.
   등록 자체는 막지 않되 실행·편집 버튼을 비활성화한다

### 4.4 동시성

같은 `cache_key`로 동시 요청이 들어와도 빌드는 한 번만 일어나야 한다. `cache_key`에 unique
제약을 걸고 삽입 충돌 시 기존 레코드를 따라간다. 이미 `BUILDING`인 키를 요청한 자산은
해당 빌드의 완료를 구독한다.

### 4.5 데이터 모델

`prizm-backend`가 소유한다. 빌드는 상태 기계이므로 조회 전용인 AI Hub가 아니라 백엔드가
맡는 것이 맞다.

```
environment_build
  cache_key          PK, 16자
  base_image_ref     표시용 태그 (pytorch-2.4-yolo12-py311-cu124:v3)
  base_image_digest  불변 다이제스트
  requirements_raw   사용자 입력 원문
  requirements_norm  정규화 결과
  recipe_version
  status             PENDING | BUILDING | READY | FAILED
  image_ref          prizm/env:<cache_key>  (READY일 때)
  build_log_ref      MinIO 경로
  error_summary
  created_at / started_at / finished_at
```

requirements는 자산 **버전마다** 다르므로 환경은 자산 버전 단위로 연결된다. 다만 코드
자산을 영속화하는 저장소가 아직 없다(§4.6). Phase 1에서는 설정으로 바인딩된 단일 자산에
requirements를 부여해 파이프라인을 검증하고, 자산 버전 ↔ `cache_key` 매핑 테이블은 자산
영속화 과제에서 도입한다.

### 4.6 전제: 코드 자산 영속화는 아직 없다

현재 `prizm-backend`의 엔티티는 `Run` 하나뿐이고, 코드 자산은 `application.yml`에 설정으로
바인딩된 단일 레코드(`CodeAssetProperties`)와 AI Hub의 JSON 카탈로그로만 존재한다. 포털의
"코드 등록" 대화상자는 화면만 있고 저장되는 곳이 없다.

따라서 **"등록 화면에서 requirements를 입력받아 자산에 저장한다"는 흐름은 지금 구현할 수
없다.** 이 설계는 그 의존성을 다음과 같이 처리한다.

- **Phase 1 범위에서 제외**한다. 대신 설정 바인딩된 기존 자산에 requirements를 부여하는
  경로로 파이프라인 전체를 검증한다. 빌드 트리거는 등록 화면이 아니라 백엔드 API로 둔다
- 자산 영속화(코드 자산을 DB에 저장하고 등록 화면과 연결)는 **별도 선행 과제**이며, 이
  기능의 사용자 대면 완성에는 그 과제가 필요하다
- 그 과제가 끝나면 등록 화면에 requirements 입력을 붙이고, 자산 버전 저장 시 §4.3의 빌드를
  자동 트리거하도록 연결한다

이 분리를 지키면 Phase 1은 자산 영속화를 기다리지 않고 독립적으로 완료·검증할 수 있다.

## 5. 실행 경로 통일 (Phase 1)

### 5.1 현재 구조

`mlops_notebook_executor.py`의 `execute_notebook`은 `PythonOperator`이며 Airflow 워커
프로세스 안에서 `pm.execute_notebook()`을 직접 호출한다. 그래서 torch·ultralytics가
Airflow 이미지에 구워져 있다.

### 5.2 변경 내용

`execute_notebook` 태스크를 `DockerOperator`(프로토타입) 또는 `KubernetesPodOperator`(운영)로
교체해, 자산의 `image_ref` 컨테이너 안에서 papermill이 실행되도록 한다. 다음이 컨테이너
경계를 넘어야 한다.

- **출력 경로**: 백엔드는 papermill autosave가 갱신하는 출력 `.ipynb`를 읽어 SSE로
  스트리밍한다. 자식 컨테이너에도 `runs` 볼륨을 동일 경로로 마운트해야 이 경로가 유지된다
- **자격증명·엔드포인트**: `MLFLOW_TRACKING_URI`, `MLFLOW_S3_ENDPOINT_URL`, MinIO 키를
  자식 컨테이너 환경변수로 전달
- **네트워크**: 자식 컨테이너가 mlflow·minio에 닿아야 하므로 동일 compose 네트워크에 참여
- **도커 소켓**: `DockerOperator`는 Airflow 컨테이너가 호스트 도커 소켓에 접근해야 한다.
  보안상 **프로토타입 한정**이며, 운영은 Kubernetes로 가야 하는 주된 이유다

### 5.3 완료 기준

기존 E2E가 그대로 재현되어야 한다.

- 성공 경로: 오늘 검증한 RUN-27006과 동등한 실행(진행률·실시간 노트북 스트리밍·MLflow
  모델 등록·결과 스트립)이 파생 이미지 경유로 동작
- 실패 경로: RUN-27007과 동등하게 `epochs=0` 입력 시 `ValueError`가 오류 셀로 표시
- 신규: requirements를 지정한 새 자산이 그 패키지를 실제로 import하는 노트북을 성공 실행

## 6. 편집 세션 (Phase 2 — 아키텍처 수준)

Phase 2는 착수 전에 별도 spec으로 상세화한다. 여기서는 Phase 1의 인터페이스를 구속하는
범위까지만 확정한다.

- **세션 생성**: `POST /api/edit-sessions {assetId, version}` → 자산의 `image_ref`로 컨테이너를
  기동하고 JupyterLab을 1회용 토큰과 `base_url=/edit/<sessionId>/`로 실행. MinIO에서 대상
  `.ipynb`를 작업 디렉터리로 복사
- **프록시**: 백엔드가 `/edit/<sessionId>/**`를 해당 컨테이너로 리버스 프록시하고 세션
  소유자만 통과시킨다. 포털과 **동일 오리진**이 되어 iframe CSP·쿠키 문제를 피한다.
  커널 통신을 위해 **WebSocket 프록시가 필수**다
- **체감 속도**: 버튼 클릭 시 화면은 즉시 전환하고 "실행 환경 연결 중" 칩만 표시한다.
  캐시 히트 시 실측 기준 6~8초 안에 커널이 붙으며, 그동안 사용자는 노트북을 읽는다
- **세션 재사용**: 사용자당 1세션을 유지해 두 번째 노트북부터는 대기가 없다. 유휴 30분에
  회수하되, 회수 전에 드래프트를 MinIO에 저장해 편집 내용을 잃지 않는다
- **저장 정책**: 자동저장은 컨테이너 내 파일과 MinIO 드래프트 경로에만 반영된다. 자산의
  새 버전이 되려면 "새 버전으로 등록"을 명시적으로 눌러야 하며, 기존 버전은 불변이다

## 7. 위험과 완화

| 위험 | 영향 | 완화 |
|---|---|---|
| Airflow 실행 경로 변경 회귀 | **최대 위험**. 오늘 검증한 실행 체인이 통째로 바뀐다 | §5.3의 기존 E2E 재현을 Phase 1 완료 게이트로 삼는다 |
| WebSocket 프록시 복잡도 | 커널이 붙지 않으면 편집 기능 자체가 무의미 | Phase 2 착수 시 최우선 검증. 동일 오리진 단순 프록시로 시작하고, 막히면 포트 직결로 폴백 |
| 호스트 도커 소켓 노출 | 컨테이너 탈출 시 호스트 장악 | 프로토타입 한정임을 문서에 명시. 운영은 Kubernetes |
| 파생 이미지 증식 | 자산×버전마다 이미지가 쌓여 스토리지 압박 | 캐시 키 공유로 중복 제거 + 일정 기간 미참조 이미지 GC |
| 폐쇄망 패키지 설치 실패 | 등록은 됐는데 실행이 안 되는 자산 발생 | 등록 시점에 빌드해 즉시 발견. 어떤 패키지가 왜 실패했는지 로그를 화면에 노출 |

## 8. 이번 범위에서 제외

- GPU 스케줄링·할당 (현재 프로토타입은 CPU)
- 다중 노드 분산 실행
- 동시 협업 편집 (여러 사용자가 한 노트북을 동시에)
- 편집 환경 내 터미널 접근
- 사용자 정의 베이스 이미지 업로드 (베이스는 큐레이션된 12종으로 한정)
- 코드 자산 카탈로그의 AI Hub 실데이터 연동 (별도 후속 과제)
- 코드 자산 영속화와 등록 화면 연동 (별도 선행 과제, §4.6)

## 9. 단계별 산출물

| 단계 | 범위 | 완료 기준 |
|---|---|---|
