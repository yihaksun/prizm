# PRIZM 디자인 개선안 · 퍼블리싱 인계서

작성일: 2026-09-13

이번 산출물은 디자인 설계다. 기존 화면의 기능, 메뉴, 데이터, 데모 흐름을 바꾸는 요청이 아니다. 아래 수치는 구현의 시작값이며, 실제 화면에서 줄바꿈·대비·정보량을 검증해 확정한다.

## 1. 디자인 결론

**정밀한 제조 시스템의 구조 위에, PRIZM을 통과하는 빛의 성격을 얹는다.**

PRIZM에는 이미 차별화할 소재가 있다. 하나의 파이프라인, 프리즘, 여러 모델, 세계 공장이라는 서사다. 새 장식 모티프를 추가하기보다 이 서사의 형태·색·움직임을 화면 전반에서 일관되게 사용한다.

사용자가 느껴야 할 인상은 세 가지다.

- 첫 화면: 현대자동차의 제조 AI 플랫폼이라는 정체성이 보인다.
- 업무 화면: 정보의 우선순위가 명확하고 오래 읽어도 피곤하지 않다.
- 자산 화면: 이 회사의 실제 데이터와 작업 결과가 보인다. 샘플 대시보드처럼 보이지 않는다.

브랜드 표현은 홈에 집중하고, 상세 화면으로 들어갈수록 배경과 장식을 줄인다. 모든 페이지를 홍보용 랜딩 페이지처럼 만들지 않는다.

## 2. 확인한 화면과 레퍼런스

- 현재 로컬 홈과 코드 자산 목록을 1600×1000 화면으로 직접 확인했다.
- 홈의 대형 어두운 프리즘 영역, 아래 작업 영역, 코드 목록의 검색·필터·카드 구조를 확인했다.
- 공통 스타일, 홈, 프리즘, 공통 모달 코드를 검토했다. 다른 모든 페이지와 모달을 이번에 시각 검증한 것은 아니다.
- [WEBON 라이플립 사례](https://webon.cc/portfolios/liflip)의 소개 페이지와 실제 ERP 대시보드 이미지도 구분해서 확인했다.

레퍼런스에서 가져올 것은 화면 전체의 색조를 맞추는 방식, 콘텐츠에 따른 면적 배분, 넓고 좁은 영역의 리듬이다. 소개 페이지의 크림색 배경·큰 여백·기기 목업은 포트폴리오 연출이다. 실제 ERP는 어두운 내비게이션과 밝은 업무 패널을 사용한다. 그 제품의 조밀한 카드 배열까지 복제할 이유는 없다.

현대자동차 공식 CI 색은 [전용색상 안내](https://www.hyundai.com/kr/ko/info/ci/ci-color)를 기준으로 한다. 아래의 적용 비율, UI 중간색, 그림자 등은 PRIZM을 위한 제안이며 공식 사내 UI 규정이라는 뜻은 아니다.

## 3. 현재 화면의 구체적인 문제

| 관찰 | 사용자가 받는 인상 | 개선 |
|---|---|---|
| 홈 상단은 큰 어두운 그래픽, 하단은 작은 글씨와 테두리 중심 | 상단과 하단이 별도 제품처럼 보임 | 같은 정렬선과 색온도로 연결하고 그래픽의 면적 조정 |
| 작업·성과·거점·실행 영역에 강조선 반복 | 중요하지 않은 요소까지 똑같이 강조됨 | 장식용 색 테두리 제거, 제목·수치·면적·간격으로 위계 설정 |
| 일부 설명과 보조 라벨이 매우 작고 영문 모노스페이스 사용이 잦음 | 읽기보다 분위기를 위한 UI처럼 보임 | 일반 정보는 본문 서체, 코드·ID만 모노스페이스 |
| 코드 목록에 검색 상자, 결과 상자, 카드 상자가 겹침 | 화면이 칸막이로 잘게 나뉨 | 목록을 감싼 외곽 상자를 없애고 검색과 카드 관계 단순화 |
| 코드 썸네일이 대부분 비슷한 어두운 그래프 | 개별 자산의 차이가 보이지 않음 | 실제 노트북 출력과 내용에 따른 썸네일 |
| 아이콘의 형태보다 색 상자와 테두리가 눈에 띔 | 일반적인 템플릿의 부품처럼 보임 | 주요 자산용 아이콘만 고유화하고 불필요한 아이콘 배경 제거 |

생성형 도구를 썼는지 여부는 화면만으로 판단할 수 없다. 개선 대상은 위와 같은 반복 패턴이다.

## 4. PRIZM만의 세 가지 시각적 특징

### A. 방향이 있는 빛

배경에 무작위 보라·파랑 원형 그라데이션을 넣지 않는다. 프리즘에서 나온 빛처럼 시작과 방향이 있는 얇고 넓은 색면을 사용한다.

- 홈의 브랜드 헤더 뒤에 한 개의 넓은 사선 면을 배치한다.
- 사선은 승인된 Z 로고의 기울기에서 가져온다. 임의의 다른 각도를 여러 개 쓰지 않는다.
- 색은 Light Sand를 바탕으로 Sky Blue 계열이 아주 옅게 비치는 정도로 제한한다.
- 색면은 제목·본문 뒤에서 복잡하게 겹치지 않고, 우측 여백 쪽에서 더 보이도록 한다.
- 무지개는 로고의 Z와 프리즘의 분광에 집중한다. 버튼·카드·테이블에는 확산하지 않는다.
- 본문을 스크롤해 내려가면 배경은 거의 단색이 된다. 고정 배경 애니메이션은 사용하지 않는다.
- 기존 격자·점·광선 표현에 또 장식을 더하지 않는다. 배경을 바꾸면 중복되는 격자와 패턴은 줄인다.

차별점은 ‘그라데이션을 썼다’가 아니라, 모든 빛의 방향에 PRIZM의 근거가 있다는 것이다.

### B. 하나로 이어지는 업무 면

화면 전체를 카드로 채우지 않는다. 넓은 밝은 바탕 위에 제목, 표, 작업 항목이 정렬되고, 선택 가능한 자산만 독립적인 카드로 떠 있는 구성을 만든다.

- 페이지 배경: 따뜻한 밝은 회색.
- 읽고 작업하는 면: 흰색.
- 독립 자산 카드: 흰색과 아주 옅은 테두리.
- 모달: 불투명 흰색과 분명한 그림자.
- 같은 영역에서 ‘외부 카드 → 내부 카드 → 또 다른 카드’ 구조를 만들지 않는다.
- 테이블을 감싼 별도 강조 박스는 제거하고 헤더·행·간격만으로 구조를 만든다.
- 카드 상단이나 왼쪽의 색 띠를 상태 표현의 기본 도구로 사용하지 않는다.

선택 탭, 키보드 포커스, 표의 구분선처럼 기능적인 선은 유지한다. 모든 선을 지우라는 뜻이 아니다.

### C. 실제 제조 결과가 디자인이 되는 썸네일

자산마다 랜덤 일러스트나 비슷한 그래프를 넣으면 다시 템플릿처럼 보인다. 실제 내용의 차이가 카드의 차이가 되어야 한다.

| 종류 | 썸네일 원칙 | 피할 것 |
|---|---|---|
| 데이터 | 실제 샘플 이미지 2~4개, 필요 시 Labels 표시 | 모든 데이터에 같은 공장 사진 |
| 코드 | 노트북의 대표 출력: 검출 결과, confusion matrix, 손실 곡선 등 | 출력과 무관한 가짜 차트 |
| 모델 | 대표 검출 결과 또는 승인된 평가 비교 이미지 | 모든 모델에 같은 3D 큐브 |
| 출력 없는 코드 | 실제 첫 Markdown 제목과 읽을 수 있는 짧은 코드 일부 | 의미 없는 코드 무늬 |

카드의 동일성은 썸네일 색상이 아니라 과제명·제목·메타정보·여백의 규칙으로 만든다. 예를 들어 용접 검출 학습 코드는 용접 이미지와 학습 곡선, 평가 코드는 실제 confusion matrix가 보이면 된다. 서로 다른 콘텐츠를 동일한 프레임 안에 놓는다.

외부에서 가져온 임의 HTML을 카드에서 실행하지 않는다. 기존의 노트북 미리보기 방식에 맞춰 안전한 정적 대표 출력 또는 명시적으로 선택한 커버를 사용한다. 이번 목업에서는 실제 예시 출력 기반의 고정 이미지를 연결해도 된다. 자동 생성 백엔드는 별도 범위다.

| 전체 배경 | Hyundai Light Sand `#F6F3F2` | 홈과 목록의 기본 배경 |

E-FOREST 녹색은 로고 정체성에 우선 사용한다. 화면 전체의 두 번째 포인트색으로 확장하지 않는다. 상태색은 위험·주의·완료에만 사용하고 반드시 상태 텍스트를 함께 표시한다. Active Blue를 작은 본문 글자의 기본색으로 쓰지 않는다.

배경 색면의 시작값은 색 자체의 불투명도 8~12%다. 미묘한 차이이므로 스크린샷에서 확인해야 한다. 본문 영역은 투명도를 주지 않는다. 흐릿한 글씨와 유리 패널로 분위기를 만들지 않는다.

## 6. 타이포그래피와 간격

현재의 Pretendard Variable을 공통 본문 서체로 유지한다. 새 폰트를 섞기 전에 글자 크기·무게·행간·색을 바로잡는다. 승인된 PRIZM 문구의 문장, 개행, Z 처리도 유지한다.

| 요소 | 크기 / 무게 / 행간 시작값 |
|---|---|
| 페이지 제목 | 28~32px / 600 / 1.25 |
| 섹션 제목 | 20px / 600 / 1.4 |
| 자산 제목 | 17px / 600 / 1.4 |
| 기본 본문 | 15px / 400~450 / 1.55 |
| 표·폼·보조정보 | 14px / 400~500 / 1.45 |
| 제한된 메타 라벨 | 12px / 500 / 1.4 |
| 주요 KPI | 32~36px / 550~600 / 1.15 |
| 상위·하위 메뉴 | 15px·14px / 500 / 1.4 |

- 업무에 필요한 상태·버전·마감·수치는 12px 미만으로 줄이지 않는다.
- 모노스페이스는 코드, 자산 ID, 복사 가능한 기술 문자열에만 쓴다.
- 일반 숫자는 같은 서체의 tabular-nums로 정렬한다.
- 의미 없는 영문 대문자 소제목과 과도한 자간은 줄인다. 메뉴 구조를 알려주는 실제 경로는 필요할 때만 표시한다.
- 공통 간격: 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px.
- 콘텐츠 좌우 여백: 1440px 이상에서 40px, 1280px 안팎에서 24px.
- 섹션 사이: 40~48px. 제목과 내용 사이: 20~24px. 카드 내부: 20~24px.
- 모서리: 카드 8px, 입력·버튼 6px, 모달 12px. 모든 것을 둥근 pill로 만들지 않는다.

## 7. 홈 화면 재구성

기존 1~5번 섹션 순서와 재무 기여의 최하단 배치를 유지한다. 섹션마다 색이나 장식을 새로 만들지 않는다.

### 첫 화면

상단 브랜드 문구와 그림은 하나의 구성으로 읽히도록 좌우 정렬선을 맞춘다. 결합 로고 크기를 키우지 않는다. 왼쪽 사이드바 로고보다 더 커 보이지 않게 한다.

- 1440×900 기준, 글로벌 헤더 64px 아래 브랜드 소개 72~80px.
- 프리즘 그림은 약 280~300px 높이에서 시작한다. 현재 1600×1000 캡처의 약 390px보다 낮추되 내부 오브젝트를 단순 축소하지 않는다.
- 그래픽의 불필요한 상하 여백을 줄이고 공장·프리즘·지구의 연결선이 읽히도록 재배치한다.
- 우측 지표 영역은 약 220~240px 확보한다. 긴 한글 라벨이 10px 수준으로 줄어들지 않게 한다.
- 공장·대륙·흰 파이프라인은 또렷하게, 배경 격자·보조 경선·잔광은 약하게 한다.
- 어두운 그림과 밝은 업무 부분 사이에 32~40px 여백을 둔다. 화면 전체에 회색 상자를 추가해 연결하지 않는다.
- 필터 도구막대는 약 44px, 그 아래 오늘의 작업 제목과 최소 1개 작업의 판단·진입 버튼까지 첫 화면에서 보이게 한다.

홈을 연 순간 브랜드만 보이거나, 작업에 접근하기 위해 긴 소개를 스크롤해야 해서는 안 된다.

### 01 오늘의 작업

두 개의 색 테두리 카드를 ‘내가 판단해야 할 작업 두 건’으로 보이게 바꾼다.

- 같은 높이의 두 작업 면을 쓰되 상단 파란 선과 왼쪽 주황 선은 제거한다.
- 우선순위는 `성능 검토 필요` 같은 상태 텍스트와 작은 표식으로 표현한다.
- 제목 다음에 ‘어디에서 무엇이 달라졌는지’를 한 줄로 보여준다.
- 실제 데이터가 있으면 전/후 수치 또는 대표 불량 이미지 하나를 보여준다. 알 수 없는 비교 수치를 새로 만들지 않는다.
- 카드 전체를 애매하게 클릭시키기보다 `원인 및 조치 검토`, `비교 결과 검토`를 일관된 위치에 둔다.
- 최근 변경은 같은 제목·행 구분 규칙의 간단한 목록으로 두고, 새로운 운영 브리핑 카드를 추가하지 않는다.

### 02 거점 운영

기존 매트릭스가 적합하다. 별도의 색 프레임을 없애고 거점명·운영 모델·이상·마지막 배포를 읽기 쉬운 표로 정리한다. 모든 수치를 배지로 만들지 않고 문제가 있는 상태만 표시한다. 선택한 거점의 상세 연결은 유지한다.

### 03 파이프라인 현황

실행 이름, 상태, 진행 단계, 경과 시간을 같은 행에서 읽도록 한다. 진행률을 큰 카드의 장식으로 쓰지 않는다. 실제 진행 상태가 있는 행만 움직이고 완료 행은 정적인 상태로 둔다.

### 04 성과 근거

기존 근거 표를 유지한다. 값·대상·기간·산정 근거의 정렬을 정돈하고 강조선과 과도한 배지를 제거한다. 재무 기여와 연결되는 근거임을 읽을 수 있게 한다.

### 05 재무 기여

하나의 넓은 면 안에 총 기여액을 가장 크게, 투자·작업시간·손실 절감 내역을 같은 기준선에 배치한다. 네 개의 동일한 KPI 상자를 반복하지 않는다. 기간과 산정 기준은 금액 옆 또는 바로 아래에 표시한다. 추정치와 확정치가 구분되는 기존 정보가 있으면 유지하며 성과 수치를 과장하지 않는다.

## 8. 코드·데이터·모델 목록과 상세

### 목록의 공통 틀

`페이지 제목 + 주 행동 → 검색 → 필터 → 결과 수·정렬 → 자산 카드`

검색·탭·필터를 각각 큰 상자에 넣지 않는다. 코드 화면에서는 현재 3단 검색 상자를 2단 도구 영역으로 정돈하고 결과 목록 외곽 패널을 제거한다. 필터 기능을 삭제하는 것은 아니다.

- 첫 줄: 검색과 필요한 보기 선택.
- 다음 줄: 내 코드·공유받음 등의 범위, 메타정보 필터. 공간이 부족하면 필터만 다음 줄로 자연스럽게 넘긴다.
- 검색결과 수와 정렬은 카드 위의 작은 한 줄로 배치한다.
- 1440px 이상에서 카드 3열, 여유가 부족하면 2열. 카드 최소 폭 약 300px, 간격 20px.
- 과제명은 모든 자산 카드에서 제목 위 첫 번째 텍스트 위치에 유지한다.
- 썸네일 높이 140~160px, 제목 최대 2줄, 설명 최대 2줄. 상세에서 전체 정보를 읽을 수 있게 한다.
- 같은 행 카드의 제목·메타정보 기준선을 맞춘다. 태그 개수 때문에 높이가 제각각 벌어지지 않도록 한다.
- 호버는 테두리 명도와 아주 약한 그림자로만 표현한다. 카드가 위로 튀거나 확대되지 않는다.

### 상세의 공통 틀

`과제명 → 자산 제목·버전 선택 → 설명·메타정보 → 콘텐츠 탭 → 본문`

- 다운로드와 SDK 스니펫은 같은 크기의 보조 행동으로 오른쪽에 둔다.
- 코드 편집과 이 버전으로 실행은 의미를 구분한다. 실행을 주 행동으로 두되 문맥에 맞는 기존 위치를 존중하고 중복 버튼을 만들지 않는다.
- IPYNB는 파일 형식 표식이다. 네이비 버튼처럼 채우지 않고 작은 파일 아이콘과 텍스트로 표시한다.
- 코드 본문은 실제 HTML 노트북 미리보기를 유지한다. 가짜 코드 블록으로 대체하지 않는다.
- 노트북 목차는 기존 별도 reader에서만 유지한다. 상세 본문 폭을 줄이는 추가 사이드 패널을 만들지 않는다.
- 연관 자산은 출처와 연결을 읽을 수 있는 짧은 목록으로 표시한다. 거대한 리니지 일러스트를 매번 넣지 않는다.
- 모델 평가 화면은 실제 입력과 예측·Labels의 비교 자체를 주인공으로 삼는다. 장식용 지표 카드를 앞에 쌓지 않는다.

## 9. 아이콘

Lucide 전체를 다른 라이브러리로 교체하는 것만으로는 차별화되지 않는다. 검색·닫기·다운로드·확대 등 익숙한 행동 아이콘은 그대로 두고, 주요 자산과 업무를 나타내는 소수의 아이콘만 PRIZM 전용으로 설계한다.

| 대상 | 기본 형태 |
|---|---|
| 데이터 자산 | 이미지 프레임과 한 장의 겹친 레이어 |
| 코드 자산 | 문서 안의 노트북 셀 두 개 |
| 모델 자산 | 세 면이 구분되는 작은 입체 구조 |
| 실행 | 하나의 입력과 분기한 출력 노드 |
| 평가 | 같은 프레임 안의 비교 면 두 개 |
| 배포 | 중심에서 대상 노드로 연결되는 형태 |

- 24×24 기준, 실제 표시 18~20px, 선 두께 약 1.6px.
- 기울어진 모서리를 넣는다면 로고의 기울기를 한 군데만 사용한다. 모든 도형을 억지로 Z로 만들지 않는다.
- 기본은 단색. 선택 상태에서 필요한 면 하나만 채운다.
- 아이콘마다 다른 형광색 배경 상자를 만들지 않는다.
- 반드시 텍스트 라벨과 함께 사용한다. 고유 아이콘 때문에 메뉴 의미가 모호해지면 기존 형태를 우선한다.
- SVG 컴포넌트로 관리한다. 메뉴마다 다른 크기의 PNG를 끼워 넣지 않는다.

## 10. 공통 모달과 움직임

모달의 여유는 바깥 크기를 키우는 것만으로 해결하지 않는다. 헤더·본문·하단 행동의 역할을 나눈다.

- 일반 모달 560~640px, 실행 설정처럼 복잡한 모달 800~880px에서 시작한다.
- 뷰포트 상하 여백 최소 32px. 작은 높이에서는 본문만 스크롤한다.
- 헤더 좌우·상단 여백 24~32px. 본문 그룹 사이 24px. 하단 행동 영역 상하 20~24px.
- 헤더와 하단은 불투명 흰색. 뒤의 본문이 비쳐 보이지 않게 한다.
- 필드 높이 40~44px, 버튼 높이 40px. 외부 배경에는 약한 dim만 적용한다.
- 공통 DialogFooter에 있는 음수 margin과 개별 모달 padding의 결합을 먼저 점검한다. CSS 끝에 임시 덮어쓰기를 누적해 해결하지 않는다.
- 입력 레이블, 선택 항목, 버튼이 각각 어떤 정보를 다루는지 알 수 있어야 한다.

호버·포커스 전환은 140~180ms, 모달은 160~200ms 정도에서 시작한다. 프리즘의 빛은 6~8초 정도의 느린 흐름으로 제한하고 지속적인 번쩍임을 줄인다. 모션 감소 설정에서는 정적인 화면을 제공한다. 이전에 제거한 로딩 로고·브랜드 인트로·강제 지연을 재도입하지 않는다.

## 11. 구현 범위와 순서

### 첫 번째 적용 단위

공통 색·서체·간격, 홈, 코드 자산 목록·상세, 실행 설정 모달을 먼저 맞춘다. 이 조합으로 브랜드 표현, 목록 밀도, 긴 본문, 복잡한 폼을 모두 검증할 수 있다.

1. 현재 스크린샷과 기능 동작을 기록한다.
2. 색·크기·간격 토큰을 정리하고 중복 CSS를 확인한다.
3. 홈의 프리즘 높이·작업 영역·섹션 제목 규칙을 적용한다.
4. 코드 목록 외곽 상자와 썸네일을 정리한다.
5. 상세 헤더와 공통 모달을 정돈한다.
6. 1440×900, 1600×1000, 1280×800에서 시각 검증한다.
7. 검증한 규칙을 데이터·모델·평가·실험·모니터링·자원 화면으로 확장한다.

### 구현자가 확인할 파일

- `app/globals.css`: 토큰과 누적된 컴포넌트 스타일. 무조건 전면 삭제하거나 마지막에 전역 override를 쌓지 않는다.
- `app/page.tsx`, `components/prizm-hero.tsx`: 홈과 브랜드 그래픽.
- `components/code-assets-workspace.tsx`: 코드 자산, 메뉴와 공통 화면 구조의 일부.
- `components/portal-workspace-tabs.tsx`: 메뉴 기준 작업 탭.
- `components/data-assets-workspace.tsx`, `components/model-assets-workspace.tsx`: 자산 목록·상세 일관성.
- `components/ui/dialog.tsx`, `components/asset-sdk-dialog.tsx`: 공통 모달과 SDK 행동.
- 평가·프로젝트·자원·작업 화면 컴포넌트: 공통 규칙 확장 시 개별 폼·상태 검증.

실제 컴포넌트 의존관계를 확인한 후 공유 범위를 정한다. 디자인 작업을 이유로 전체 라우팅이나 데이터 구조를 재작성하지 않는다.

## 12. 유지해야 할 제품 결정

- 승인된 PRIZM·E-FOREST 로고 원본, 다크 사이드바 로고, 브랜드 문구와 Z 처리.
- 기존 메뉴명, 과제 귀속, 자산 ID·버전 규칙.
- 메뉴 기준 작업 탭, 최초 열린 순서, 모두 닫기 시 홈 이동.
- 코드·데이터·모델은 목록에서 선택한 뒤 상세로 이동.
- 버전 선택, 다운로드, SDK 스니펫, 연관 자산 링크.
- 코드 편집과 실행의 구분, 사전 점검·즉시 실행·스케줄링.
- 실행 자원과 실행 환경의 독립 선택.
- 이상 감지 → 담당자 병렬 확인 → 데이터 준비 → 실험 → 평가 → 배포 → 모니터링 데모 연결.
- 재무 기여는 홈 맨 아래. 모달·작업 탭·자산 내용이 디자인 변경으로 사라지지 않게 한다.

## 13. 금지 패턴

- 모든 카드의 상단 또는 왼쪽에 색 띠 추가.
- 배경 전면에 무작위 다색 그라데이션, 노이즈, 격자, 광선을 동시에 사용.
- 반투명 업무 카드, 흐려진 본문, 유리 재질의 폼.
- 기능 의미가 없는 영문 라벨·일련번호·실시간 점멸 표시 추가.
- 코드·데이터·모델을 모두 동일한 이미지 카드로 변경.
- 성능 수치와 관계없는 랜덤 차트 생성.
- 모든 버튼을 원색 또는 네이비로 채우기.
- 글씨를 작게 만들어 억지로 한 줄에 넣기.
- 대시보드 섹션마다 새로운 테마, 그림자, 모서리, 제목 체계 사용.

## 14. 완료 판단

- 로고를 가려도 빛의 방향, 색온도, 자산 콘텐츠의 표현에서 PRIZM의 성격이 남는가?
- 첫 화면에서 사용자가 확인할 작업과 진입 버튼이 보이는가?
- 홈과 코드 목록이 같은 제품으로 보이는가?
- 카드의 색 띠를 없앤 뒤에도 상태·선택·행동이 분명한가?
- 일반 본문 대비 4.5:1 이상을 확인했는가? 작은 글씨를 흐리게 해서 위계를 만들지 않았는가?
- 1280px에서도 제목·버튼·메뉴가 겹치지 않고, 긴 표만 자신의 영역에서 스크롤되는가?
- 키보드 포커스와 드롭다운 항목이 잘 보이고 모달 밖에 가려지지 않는가?
- 실제 자산의 대표 출력과 썸네일 내용이 일치하는가?
- 디자인 때문에 기존 작업 탭·실행·버전 선택·다운로드·연관 자산 연결이 손상되지 않았는가?

최종 검토는 첫 화면 한 장으로 끝내지 않는다. 홈, 코드 목록, 코드 상세, 실행 모달, 데이터·모델 목록, 평가 상세를 같은 화면 크기로 놓고 비교한다. 모든 화면을 동일한 카드로 만드는 것이 아니라, 같은 규칙으로 각 업무를 표현하는 것이 목표다.
